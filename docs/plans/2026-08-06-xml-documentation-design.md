# XML Documentation — Design (Phase 4.2's blocker)

**Date:** 2026-08-06
**Milestone:** 4 — Release Readiness
**Status:** approved (design)

## 0. Why this is a blocker and not a chore

Three facts combine into one:

- **`GenerateDocumentationFile` is set nowhere** — verified across every `.props`, `.csproj` and
  `.targets` in the repository.
- **CS1591 is not suppressed** anywhere.
- **`TreatWarningsAsErrors` is `true`.**

So every one of the 66 packages currently publishes **with no IntelliSense XML at all** — no
parameter hints, no summaries, nothing in a consumer's IDE — and the moment generation is enabled,
every undocumented public member becomes a **build error**. There is no partial state: the build is
either green with no documentation shipping, or red until the last member is documented.

That is permanent once the package IDs are on nuget.org, which is why Phase 4.1 recorded it with a
hard wall at **6.3**. It was scoped to 4.1 on 2026-07-28 and skipped; 4.1's close says so rather
than absorbing it.

## 1. The measurement — one project, not sixty-six

The roadmap describes this as repo-wide ("enable generation, clear the cref backlog"). Measured by
enabling generation with CS1591 demoted to a warning and counting distinct diagnostics:

| Source | Undocumented public members | Ours to fix? |
|---|---|---|
| **`Rag.NET.Abstractions`** (hand-written) | **172** | yes |
| `Rag.NET.Abstractions` (`ZeroAlloc.ValueObjects` generated) | **~24** | **no** |
| `Rag.NET.RepoConventions.Tests` | 30 | not shipped |
| **All 65 other packages** | **0** | — |

**The library is already almost entirely documented.** The work is one project's public model and
options surface.

The concentration is itself useful: `RagOptions` (14), `RetrievalOptions` (8), `TextChunk` (7),
`IRagDataManager` (7), `DocumentSummary` (7), `DocumentSection` (7). These are exactly the types
where defaults, units and valid ranges are what a consumer needs and cannot guess.

## 2. Test projects are excluded, not documented

`tests/Directory.Build.props` sets `GenerateDocumentationFile=false`.

Test projects are not packable and never ship. Documenting 30 members there would produce
documentation no consumer can ever read, purely to satisfy a compiler flag.

## 3. The 172 get documentation that adds information

**Document what a consumer cannot infer** — units, defaults, valid ranges, what `null` means, what
the store clamps versus what we clamp, side effects. **Never restate the member name.**

```csharp
// Restating the name — worse than nothing:
/// <summary>Gets the TopK.</summary>

// Adding information:
/// <summary>
/// Chunks to retrieve before reranking. Default 5. Values above the store's own
/// limit are clamped by the store, not here.
/// </summary>
```

**The real risk of this phase is 172 members of filler.** A doc that satisfies the compiler while
telling a reader nothing is this repository's signature defect — docs and code agreeing and both
being useless — and unlike a stale comment it would be permanent in every consumer's IntelliSense.
The implementation plan needs a check against vacuity, not merely a count of members covered.

## 4. The generated 24 gate the final step, and that is recorded

`ZeroAlloc.ValueObjects` emits `// <auto-generated />` in its output. That convention suppresses
**analyzer** diagnostics; **CS1591 is a compiler warning and is not covered by it.** The generator
would need to emit `#pragma warning disable CS1591`.

**This is an upstream defect affecting every consumer of that library who enables documentation**,
not something to work around locally. Decided 2026-08-06: **raise it upstream; do not suppress.**

The phase therefore splits:

- **Everything ours proceeds now** — the 172 members, the test exclusion, the guard.
- **`GenerateDocumentationFile=true` flips only when the upstream fix ships.** Until then the build
  stays green and nothing is suppressed.

### The fallback, recorded before it is needed

We would be gating a **6.3 hard wall on a third party's release**. If the upstream fix has not
landed by the time 6.3 is otherwise ready, the decision returns to the repository owner:

- suppress CS1591 narrowly for generated files via `.editorconfig`, or
- hand-write the four id types and drop `[ValueObject]` for them.

Recording this now stops it becoming an emergency later. **It also interacts with the pending
value-object work** — if those four types move to `struct` or `[TypedId]`, the generated shape
changes and this may resolve itself.

## 5. A guard, so it cannot regress

`PackageValidation` asserts **every packable project's produced `.nupkg` contains its XML
documentation file**.

Enabling generation once is not enough: a project added later could ship without it silently, which
is precisely how the current state arose — nobody chose it, it simply was never set. The guard is
read from the produced package, not the `.csproj`, and **must be proven to fail** by mutation, per
the house rule that a guard nobody has watched go red is not a guard.

## 6. Out of scope

Phase 4.2's other content — `IOptions` alignment, ZeroAlloc.Validation for pipeline options, the
`AddParser<T>(replaces:)` API design, and retiring the write-only `CostBudgetOptions.DatabasePath`.
That work is separable and does not gate 6.3. This design covers the blocker only.
